# Module 4: integrate shared business data and knowledge

Start with the [shared-data quickstart](README.md). Module 4 has two distinct
inputs: structured business data for NLQ, and separately authorized documents for
RAG. The eight CSVs supply the first, not the second. No NLQ/RAG runtime or external
model connection is implemented by this shared-data branch.

## 1. Structured business-data path

```text
Verified user session + question
    → resolve one accepted serving publication
    → choose an allowed data operation
    → apply the verified principal's store scope and query limits
    → retrieve reported facts and relevant metric definitions
    → answer with scope/date/version, coverage and unavailable-state caveats
```

Module 4 must not query `build.duckdb`, raw CSVs, `features.duckdb` or
`labels.duckdb`. Its database input is the same immutable `business.duckdb` used
by the other modules. Do not rebuild the pipeline inside a chat request.

## 2. Start with the existing bounded table reader

```bash
uv run python -m examples.read_shared_data --schema-only
uv run python -m examples.read_shared_data \
  --principal-id team-local-dev --view store_day \
  --start 2026-06-01 --end 2026-06-30 --limit 10
uv run python -m examples.read_shared_data \
  --principal-id team-local-dev --view metric_definitions --limit 100
```

The local principal must exist in your scope-configured build. App identity must
come from authentication, not from a tool argument generated by the LLM.

```python
from examples.read_shared_data import open_reader

def fetch_reported_daily_rows(verified_principal_id, publication_path,
                             start_date, end_date):
    reader = open_reader(publication=publication_path)
    rows = reader.read("store_day", verified_principal_id,
                       start=start_date, end=end_date, limit=1000)
    return {"artifact_id": reader.record["artifact_id"],
            "dataset_hash": reader.record["dataset_hash"],
            "as_of": reader.record["as_of"],
            "metric_view": reader.record["metric_view"],
            "rows": rows, "bounded_result": True}
```

Only named views in `data_platform.serving.VIEWS` are accepted. `ServingReader`
returns parameterized, scoped rows and enforces a 1–10,000 row limit; keyset
`read_page` exists only for a few fixed views. It has **no arbitrary SQL input or
general aggregate endpoint**. This makes it a starting data interface, not a
finished Text-to-SQL system.

The shared PostgreSQL reader (opt-in, not yet used by Module 4) offers exactly the
same operations and limits; record its `backend`, `release_id` and
`source_artifact_id` in answer provenance. Its read-only database login cannot
write, but it can read every published row: store scope is enforced by the
reader, not by that login. Never give these credentials or a raw connection to an
LLM or a generated-SQL runtime.

Do not calculate a company/month total from the first 1,000 returned rows. A
bounded result must be labeled as such. For aggregate questions, implement a
reviewed scoped aggregate operation or a separately secured SQL runtime, including
complete-population and metric-parity tests. That is Module 4 integration work;
do not bypass scope to obtain the full dataset.

## 3. Map questions to existing business views

| Question family | Reader view names | Important caveat |
| --- | --- | --- |
| Daily reported OOS, coverage or MSL | store_day, store_sku_daily, metric_definitions | Sum the right components; Unknown is not in stock and incomplete coverage must be shown |
| Sales, invoice amounts, trade discounts | commercial_period, sell_in_events | Pick one period_type; commercial date filters use period_start, not interval overlap |
| Deliveries | delivery_events | Realized deliveries only; do not infer a one-to-one invoice link |
| Planogram/display/shelf allocation | execution_visits | Select one scope_label; shelf allocation is not market share |
| Negotiation background | negotiation_context, products | Static price/cost reference and Requires review guardrails |
| OOS risk or visits | oos_predictions, visit_priority | Typed interfaces are empty/unreleased; return unavailable rather than 0% risk |
| Product claims or objection handling | Authorized document corpus, not a business view | Requires separately sourced/citable RAG documents |

Read exact field types/grains from the [Gold dictionary](v3-gold-data-dictionary.md)
or `reader.schema()`. Separate `estimated_*` views are opt-in candidates, not approved facts. If a user
explicitly asks for estimates, the trusted tool must request candidate access and
return Estimated/Unknown, coverage and Candidate status. Otherwise use Reported.
The LLM must not silently switch views or approve an estimator.

The [shared KPI specification](../solution-specifications/kpi-and-missing-store-day-handling.md) and
`metric_definitions` are authoritative: the LLM must not invent an alternate OOS,
discount, MSL or margin denominator.

## 4. If you implement Text-to-SQL later

An unrestricted read-only DuckDB connection is **not a security sandbox**. The
serving views do not enforce account scope by themselves; a direct file holder
can read other Gold tables. Do not implement `con.execute(llm_sql)` and assume
the view names or read-only flag make it safe.

The Module 4 runtime must separately provide and test:

1. A single parsed allowed SELECT/query structure; no multiple statements or
   bypass through nested SQL, comments or alternate schema names.
2. Explicit view/function allowlists; reject direct Gold/meta/internal tables,
   file/network table readers, extensions, ATTACH, PRAGMA/settings and mutations.
3. Store scope derived from a verified session for **every** query branch and
   join, including aggregates/subqueries. The model cannot select a principal.
4. Bounded query cost/time/row output and complete aggregate semantics. Do not
   silently truncate the inputs to a total or average.
5. Pinned publication/cutoff/metric view, correct grains and regression tests
   against shared KPI components. Never average daily percentages blindly.
6. Audit logging without leaking raw rows/secrets; any external model access
   must follow the team's data-sharing and permission policy.

An allowlisted tool/aggregate API is also a valid first implementation and does
not require general generated SQL. Choose the simpler interface that actually
meets the question set and scope requirements. Neither option is already supplied
as a deployed service by this branch.

## 5. Separate document/RAG path

```text
Authorized product/policy documents
    → version/permission registry
    → document parsing and chunking
    → permission-aware retrieval index
    → relevant passages with stable citations
    → answer with document versions and locations
```

Required registry metadata is defined in the module contract:
`document_id`, `version`, `content_hash`, `authorized_source`, `effective_date`,
`permission_scope` and `citation_location`. Documents, chunks and their citations
must retain that identity through retrieval. Implement ingestion/retrieval in
the Module 4 branch; do not fabricate product claims from the CSV dimensions.
Vector storage/model choice is not prescribed or provisioned by this data layer.

Business-data permission and document permission are separate checks. A sales
user's assigned stores do not automatically authorize every policy document.
Retrieved text is evidence, not an instruction to bypass tools, change identity,
export data or execute SQL. Unknown/missing documents should produce a clear
unavailable answer, not an invented citation.

## 6. Answer provenance and error behavior

For a data answer, retain at least serving artifact/publication identity, as_of,
the metric view/definition version, date range, authorized account scope and
coverage/unknown limitations. Distinguish event date from dataset cutoff and
wall-clock "today". For a document answer, cite document version and location.

- Permission failure: deny access; do not retry with a broader identity.
- Missing model release: say the prediction is unavailable, not that risk is zero.
- Missing source report: say Unknown; do not estimate it within the LLM.
- Requires review rule: explain the limitation without approving a scenario.
- Scope/date/row limit insufficient for the question: ask to narrow it or route
  to an approved aggregate operation; do not present a sample as a full result.
- Changed publication: invalidate version-dependent caches; do not combine
  rows from one build with definitions/results from another without disclosure.

## 7. Module 4 acceptance checklist

- Only business-serving data is reachable from the runtime; no evaluation files.
- Verified identity scopes both detailed and aggregate reads across all accounts.
- Shared KPI formulas match independently computed fixture examples.
- Limits/unavailable states are explicit, not disguised as zero or successful totals.
- SQL/tool injection tests and document prompt-injection tests fail safely.
- Documents are authorized/versioned and every quoted passage has a stable citation.
- Secrets, actual conversations, private documents, DB files and real scope maps
  remain outside Git; no LLM provider/data export is enabled by this handoff.
